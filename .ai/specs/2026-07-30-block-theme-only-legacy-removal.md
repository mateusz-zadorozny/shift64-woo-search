# Block Theme-Only Legacy Surface Removal

> **Status:** draft

## 📝 TLDR

After the Site Editor blocks and Product Collection adapter are available,
remove the pre-1.0 classic-theme placement hooks, shortcodes, theme-specific
takeovers, bespoke archive fragments, and admin appearance controls. Raise the
supported baseline to the modern WordPress and WooCommerce versions required
by the block and Interactivity APIs, with an explicit migration guide.

## 📝 Problem Statement

Maintaining classic hooks, Kadence integrations, shortcodes, custom
pagination interception, and Site Editor blocks would create two competing
frontends with different ownership rules. The plugin is still pre-1.0, so
this is the safe point to establish one coherent public surface.

## 📝 Proposed Solution

Ship a deliberate breaking cleanup only after every block-native replacement
is implemented. Preserve indexed data and core engine options, retain the
existing Search parent block names, remove obsolete placement surfaces, and
document exact Site Editor migration steps and rollback limits.

This spec is a release gate, not the first implementation step. It may begin
only after these specs are implemented and verified together:

1. `2026-07-30-block-theme-product-collection-integration.md`
2. `2026-07-30-composable-search-blocks.md`
3. `2026-07-30-product-filter-pill-blocks.md`
4. `2026-07-29-native-woocommerce-catalog-sorting.md`

The cleanup targets the next minor pre-1.0 release. It intentionally uses the
repository's documented 0.x breaking-change allowance, with changelog and
migration guidance in the same PR.

## 📝 Decisions

1. The supported frontend is a modern block theme using an inherited
   WooCommerce Product Collection. Classic themes and page-builder shortcode
   placement are no longer product targets.
2. Remove, rather than deprecate indefinitely, theme placement actions,
   shortcodes, Kadence-specific rendering, and custom grid/pager fragment
   replacement.
3. Preserve `shift64-woo-search/search` and
   `shift64-woo-search/modal-search`; their child migration belongs to the
   composable-search spec.
4. Keep Redis/RediSearch, indexing, CLI, autocomplete endpoint, search
   relevance, facet settings, sorting configuration, and business-logic
   options.
5. Raise the minimum versions to WordPress 7.0, WooCommerce 10.9, and PHP 8.3
   everywhere the plugin declares or documents runtime support.
6. Internal WordPress/WooCommerce filters required to adapt Product Collection
   queries remain. "No hooks" means no theme placement/output hooks and no
   theme-specific markup takeover.
7. Do not automatically edit a merchant's templates. Migration is explicit in
   Site Editor so the plugin never overwrites customized template content.

## 📝 Research

- WordPress plugins cannot safely inject or rewrite customized block-theme
  templates without taking ownership away from the merchant. Inserter
  guidance and migration documentation are safer than automatic template
  mutation.
- WooCommerce Product Collection already owns product-card rendering,
  pagination, no-results state, and router navigation. Keeping a second
  Shift64 fragment renderer creates duplicate state and incompatible history.
- The repository's `BACKWARD_COMPATIBILITY.md` treats shortcodes, parent block
  names/attributes, handles, options, and runtime declarations as protected,
  while permitting intentional pre-1.0 breaks only when documented.

## 📝 Architecture

### Removed frontend placement surfaces

Remove registration and runtime paths for:

- `[shift64_woo_search]`;
- `[shift64_woo_search_modal]`;
- `[shift64_woo_search_filters]` if introduced or present on the branch;
- archive/breadcrumb shortcodes owned only by classic result templates;
- automatic `woocommerce_before_shop_loop` filter-bar insertion;
- configurable/custom placement-hook machinery;
- archive header/title output actions;
- Kadence hook relocation, partial template rendering, and wrapper-specific
  selectors;
- hiding/replacing a theme or WooCommerce sort control;
- custom AJAX page/grid fragment replacement; and
- the mobile filter/sort tray generated by the old filter renderer.

The exact deletion list is generated with repository searches for
`add_shortcode`, theme-named classes/selectors, Woo placement actions, and the
legacy asset handles. The implementation PR must include that inventory in its
migration note so no hidden alias survives accidentally.

### Retained query integration

Keep/refactor only backend filters that are part of the new engine boundary:

- Product Collection query eligibility/adaptation;
- marker-scoped totals;
- canonical sort-option resolution where WooCommerce public PHP filters are
  the data source;
- indexing/data-change hooks;
- product visibility and stock/business-rule filters; and
- operational admin/CLI hooks unrelated to frontend placement.

Class names may change as responsibilities move out of
`Shift64_Woo_Search_Archive`, but render callbacks may not call classic Woo
templates or emit a parallel product loop.

### Bootstrap and asset graph

After removal, frontend bootstrap registers:

- metadata-based Shift64 blocks;
- their dynamic render callbacks;
- block-scoped styles;
- Interactivity API script modules; and
- the Product Collection query adapter/services.

It no longer instantiates a general classic frontend renderer solely to share
shortcode markup. Assets enqueue through block metadata only when their blocks
render. Global legacy scripts/styles are removed or narrowed to engine/debug
surfaces that still need them.

### Option cleanup strategy

Appearance/selector/placement option controls are removed from WP Admin.
Stored values are left inert for one pre-1.0 release to make rollback possible;
the plugin stops exporting them to generated SHORTINIT config when the
endpoint no longer reads them. A later explicit data-cleanup migration may
delete orphaned keys, but this spec does not destructively erase settings.

Engine options retain their existing keys and semantics. The existing archive
feature toggle is relabelled around Product Collection search integration only
if its underlying behavior remains identical; otherwise a separate migration
must be specified instead of silently reusing the key.

## 📝 Data Model

No Redis index or product data is removed. No existing active engine option is
renamed.

The following legacy configuration categories become inert:

- theme input/button/additional selectors used to enhance arbitrary theme
  fields;
- frontend placement mode/hook values;
- admin-only appearance values replaced by block supports; and
- theme-integration flags used only by removed render paths.

Before implementation, tests must build an explicit key inventory from the
admin registration/defaults/config exporter. The migration table in
documentation classifies every key as:

- retained and active;
- retained but no longer UI-exposed;
- inert for rollback; or
- removed only if it was never released/public.

The generated MU-plugin `config.php` format changes only by removing constants
that no SHORTINIT consumer reads. Setup/update regenerates it through the
existing deployment path; a generated file is never committed.

## 📝 API Contracts

### Breaking removals

- Classic/theme placement shortcodes listed above.
- Theme output action registrations and theme-specific filter behavior.
- Legacy frontend asset handles that exist only for AJAX archive fragment
  replacement or old filter/sort surfaces.
- Admin settings fields whose only purpose is removed placement/appearance.

The implementation PR must update `BACKWARD_COMPATIBILITY.md` from promises to
a dated migration record rather than silently deleting the protected-surface
entries.

### Preserved surfaces

- block names `shift64-woo-search/search` and
  `shift64-woo-search/modal-search`;
- new block names and attributes from their owning specs;
- plugin slug/text domain and class/function naming conventions;
- Redis key/index naming;
- CLI commands;
- SHORTINIT search endpoint and response unless separately versioned;
- active search/index/facet/sort option keys; and
- public hooks still used by documented engine extension points.

### Runtime requirements

Declare consistently:

- `Requires at least: 7.0`;
- `WC requires at least: 10.9` (and WooCommerce plugin-header equivalent);
- PHP `>=8.3`; and
- tested-up-to versions matching the release environment.

Update the main plugin header, `readme.txt`, `README.md`,
`BACKWARD_COMPATIBILITY.md`, Composer constraints/platform checks, CI matrix,
and runtime admin notice/activation guard where present. The release must not
claim support for a version omitted from CI.

## 📝 UI/UX

### Upgrade notice and migration guide

The changelog/readme release note leads with the breaking storefront change:

1. Switch/confirm a supported block theme.
2. Open Site Editor and edit each relevant Product Catalog, Product Search
   Results, and enabled product-taxonomy archive template.
3. Insert one inherited WooCommerce Product Collection if absent.
4. Insert Search/Modal Search where needed.
5. Insert Product Filters and configure its Filter Pills.
6. Insert Product Sort and choose/order the offered modes, or omit it.
7. Save and verify search, filters, sort, pagination, and mobile trays.
8. Remove old shortcode blocks/widgets and theme-specific placeholders.
9. Run Shift64 setup/rebuild only when the Facets or sorting schema status says
   it is required.

Include the exact Product Collection block pattern from the approved spec as a
copyable example, but emphasize that card inner blocks and styling remain
merchant-owned.

### Admin

- Remove appearance, placement, selector, and theme-takeover controls.
- Keep search behavior, indexing, Facets enablement/readiness, sorting engine,
  diagnostics, and rebuild actions.
- Facets settings remain linked from Filter Pill inspector only for
  enable/rebuild setup, not styling.
- Show an upgrade notice only to users who can manage the plugin; it links to
  the migration guide and can be dismissed per user.

### Missing template behavior

The plugin does not auto-insert output or display a public error. In Site
Editor it may show setup guidance. In WP Admin diagnostics it reports whether
eligible Product Collection blocks were observed during recent frontend debug
requests, without scanning or rewriting every customized template.

## 📝 Edge Cases & Failure Scenarios

- **Site still uses classic theme after upgrade:** search endpoint/CLI remain
  operational, but no archive controls are injected. Admin notice states the
  frontend requirement; no fatal error occurs.
- **Old shortcode remains in content:** WordPress shows literal/unknown
  shortcode behavior after removal. The pre-upgrade guide must tell merchants
  to locate and replace these before updating; a one-release admin-only
  detector may report occurrences but must not render the shortcode.
- **Cached pages contain old markup/assets:** release notes require normal page
  cache/CDN purge. Old JS must fail harmlessly against missing nodes.
- **Customized block template lacks Product Collection:** controls render setup
  guidance in editor and native search navigation still works; the plugin does
  not create a hidden loop.
- **Rollback to the prior plugin version:** inert options and unchanged Redis
  schema let the old frontend resume, provided the merchant also restores its
  prior templates/cache. New block comments remain unknown blocks to old code,
  so template backup is part of the rollback guidance.
- **Third-party code calls removed shortcodes/hooks/handles:** this is a
  documented pre-1.0 break. No compatibility aliases are retained.
- **Minimum-version failure:** activation/runtime guard stops block bootstrap
  with an actionable admin notice; CLI must return a non-zero explanatory
  error rather than fatal.
- **Generated MU config is old:** setup/update regenerates it; SHORTINIT ignores
  surplus legacy constants during a rolling rollback.

## 📝 Risks & Impact Review

- **Breaking change:** merchants must edit templates. The release cannot be a
  silent patch update; the changelog and upgrade notice are required.
- **Data safety:** index data and stored legacy options are retained, making
  code rollback possible. No destructive option migration ships here.
- **Hidden integration risk:** broad repository searches and a runtime asset/
  hook inventory test are necessary to prove theme-specific output is gone.
- **Dependency risk:** raising WordPress/WooCommerce baselines may exclude
  existing sites. Activation checks and release communication must precede
  removal, and version declarations must agree.
- **Performance:** removing global archive/filter assets reduces unrelated
  page work; block metadata scopes new assets to rendered blocks.
- **Rollback:** restore previous plugin version, prior block templates, and
  caches. No Redis downgrade/rebuild is required solely for this cleanup.
- **Scope boundary:** engine/query filters are not removed merely because they
  use WordPress hooks. Only output placement and obsolete integration methods
  are in scope.

## 📋 Phasing

- **Phase 0 — prerequisite gate and inventory.** No removal until all four
  block-native specs are implemented and QA evidence exists.
- **Phase 1 — stop legacy placement and remove competing runtime code.**
  Breaking but independently releasable as the planned pre-1.0 minor.
- **Phase 2 — admin/docs/runtime-baseline cleanup.** Ships in the same release
  train, with rollback-safe inert options.
- **Phase 3 — release verification.** Block-theme E2E and absence checks prove
  one frontend ownership model.

## 📋 Implementation Plan

### Phase 0

1. Assert prerequisite spec statuses and run their PHPUnit/PHPCS/block build/
   block-theme Playwright suites. Do not start deletion with any prerequisite
   still draft.
2. Generate and review inventories of registered shortcodes, frontend actions/
   filters, block names, scripts/styles, settings/options, generated config
   constants, and theme-named code paths. Commit the classification table to
   the migration guide before deletion.
3. Add characterization tests for every surface marked preserved, especially
   parent block fixtures, CLI, endpoint response, Redis keys, and engine
   options.

### Phase 1

4. Remove shortcode registration/render paths and theme/page-builder placement
   code. Tests assert the tags are no longer registered and preserved block
   renderers still work.
5. Remove automatic filter/sort/header placement, Kadence-specific integration,
   and custom fragment/pagination interception. Update the existing Product
   Collection ownership tests by removing `test.fail()` only where the desired
   assertions now pass.
6. Remove obsolete mobile sheet/render classes and global legacy frontend
   assets; register remaining block assets through metadata. Add a frontend
   asset manifest test for unrelated/product pages.
7. Refactor bootstrap and archive classes so only Product Collection query
   adaptation and engine hooks remain. PHPUnit proves no parallel product loop
   or Woo template renderer is called.

### Phase 2

8. Remove obsolete admin fields while retaining inert option values. Stop
   exporting unused SHORTINIT constants and test setup/update regeneration.
9. Raise and synchronize WordPress/WooCommerce/PHP requirements, runtime
   guards, CI matrices, readmes, and compatibility policy.
10. Publish the template migration guide, copyable approved Product Collection
    example, rollback steps, cache warning, and dismissible admin upgrade
    notice.

### Phase 3

11. Run PHPUnit, PHPCS, translation generation check, block build validation,
    and all block-theme E2E projects. Playwright stays outside the hermetic
    agentic validation gate as required by `AGENTS.md`.
12. QA a clean upgrade fixture containing every old shortcode/hook mode and a
    fresh install. Capture desktop/mobile search, modal, filters, sort,
    pagination, no-JS, Redis failure, Back/Forward, and classic-theme graceful
    degradation evidence.
13. Record the breaking change in `BACKWARD_COMPATIBILITY.md` and changelog;
    flip this spec/index status in the implementation PR.
